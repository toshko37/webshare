## 1. Цел

Анонимното качване през `/u` и `/u/ИМЕ` е важна функция. С нея всеки може да изпрати файл без акаунт. Досега то беше напълно отворено, без лимити. Освен това имаше уязвимост: анонимен посетител можеше да изтрие чужд файл.

Upload Guard запазва анонимното качване и добавя регулация:

1. Еднократна проверка, че посетителят не е робот.
2. Временен **пропуск за качване** след проверката.
3. Квоти на пропуска, лимити по IP, дневен лимит и праг за свободно място.
4. Блокиране на опасни типове файлове.
5. Отделен път за curl чрез кратък **код за качване**.

Влезлите потребители никога не минават през проверката и лимитите.

## 2. Режими

Режимът се избира в **Settings → Public Access → Upload (/u) mode**.

| Режим | Поведение |
|---|---|
| `verified` | **По подразбиране.** Анонимните посетители минават проверка и получават пропуск. Всички лимити важат. |
| `open` | Без проверка, както преди 3.7.0. Лимитите за размер на файл, дневен обем, диск и опасни файлове продължават да важат. Квотите на пропуска не важат, защото няма пропуск. |
| `login` | Само за влезли потребители. Съответства на старото `open_upload = false`. |

**Съвместимост.** Ако в `.config.json` липсва `upload_guard.mode`, а старото `open_upload` е `false`, режимът е `login`. Иначе е `verified`. При запис от админ панела `open_upload` се обновява, за да работи старият код.

**Важно при обновяване.** Инсталации, които досега са били с отворено качване, след обновяване минават автоматично в режим `verified`. Това е умишлено. Админът може да върне `open` от настройките.

## 3. Поток в браузъра

```
Посетител                    upload.php                         Apache
   │  GET /u                     │                                  │
   │────────────────────────────▶│ няма пропуск: заключена зона     │
   │  клик „Не съм робот“         │                                  │
   │  GET /u?guard=challenge ────▶│ подписана задача (HMAC)          │
   │  решава SHA-256 задачата     │                                  │
   │  POST /u?guard=verify ──────▶│ проверка, издаване на пропуск    │
   │◀──────── Set-Cookie ws_upass │ + код ABCD-EFGH                  │
   │  POST /u (файл, бисквитка) ──┼──────────────────────────────────▶ филтър: има бисквитка
   │                              │◀──────────────────────────────────│
   │                              │ проверка на пропуска и лимитите  │
   │◀──────── JSON + оставаща квота                                  │
```

Подробности:

- **Файлове, пуснати преди проверката, не се губят.** Те чакат и качването тръгва автоматично след проверката.
- **Ако пропускът изтече или се изчерпи по време на опашка,** текущият файл и останалите се връщат в чакащи, показва се проверката и след нея качването продължава.
- **Панелът с пропуска** показва до кога е валиден, колко файла и какъв обем остават, кода и готова curl команда.
- **Неуспешните файлове** вече се показват с причина на финалния екран. Преди грешките при качване изчезваха тихо.
- **Мобилен изглед.** Страницата получи `@media` правила за екрани под 520 px.

## 4. Методи за проверка

### 4.1 Proof-of-work (по подразбиране)

Сървърът генерира задача във формат, съвместим с ALTCHA:

```
salt      = 24 hex символа + "?expires=" + unix време (10 минути)
number    = случайно число в [0, maxnumber]
challenge = sha256(salt + number)
signature = HMAC-SHA256(challenge, секретен ключ на сървъра)
```

Браузърът получава `salt`, `challenge`, `maxnumber` и `signature`, но не и `number`. Той пробва числата подред, докато хешът съвпадне. Хешовете се смятат паралелно на партиди по 500 с Web Crypto API.

Сървърът проверява при `verify`:

1. Задачата не е изтекла.
2. Подписът е валиден, тоест задачата е издадена от този сървър.
3. `sha256(salt + number)` съвпада с `challenge`.
4. Задачата не е използвана досега. Използваните се пазят до изтичането си.

**Измерено време** при `maxnumber = 50000`:

| Среда | Най-лош случай |
|---|---|
| Node.js на сървъра, Web Crypto | 0,8 s |
| Телефон, очаквано | 2–4 s |

**Ограничение.** Proof-of-work не спира решителен нападател. Той само оскъпява масовото издаване на пропуски. Реалната защита са лимитите в раздел 6. При злоупотреба вдигни трудността или премини към Turnstile.

### 4.2 Cloudflare Turnstile (опция)

1. Създай widget в Cloudflare Dashboard → Turnstile за домейна.
2. Въведи site key и secret key в **Settings → Upload Protection**.
3. Избери **Cloudflare Turnstile**.

Ако някой от двата ключа липсва, системата ползва proof-of-work и админ панелът показва предупреждение. Тайният ключ не се връща във формата. Празно поле означава „запази стария“.

Turnstile праща данни за посетителя към Cloudflare. Това трябва да се отрази в политиката за поверителност.

## 5. Пропуск за качване

| Поле | Стойност |
|---|---|
| Идентификатор | 32 hex символа, 128 бита, в бисквитка `ws_upass` |
| Бисквитка | `HttpOnly`, `Secure` при HTTPS, `SameSite=Lax`, срок колкото пропуска |
| Код за curl | 8 символа от азбука без 0/O/1/I/L, около 40 бита, показва се като `ABCD-EFGH` |
| Срок | `pass_ttl_hours`, по подразбиране 24 часа |
| Квоти | `pass_max_files` файла и `pass_max_mb` MB |

**Откъде се чете пропускът**, по ред на приоритет:

1. Хедър `X-Upload-Pass`. Препоръчан за curl.
2. Параметър `?pass=` в URL. Работи, но кодът остава в логовете на Apache.
3. POST поле `pass`. Приема се от PHP, но Apache филтърът не го вижда, затова сам по себе си не стига.
4. Бисквитка `ws_upass`. Ползва се от браузъра.

Хедърът, URL параметърът и POST полето приемат както кода, така и пълния идентификатор.

**Срокът се сравнява с началото на заявката** (`REQUEST_TIME`), а не с края ѝ. Качване на голям файл, започнато с валиден пропуск, не се отказва, ако пропускът изтече по време на прехвърлянето. Проверено експериментално с PHP-FPM: при бавно качване `REQUEST_TIME` отчита старта.

**Пропускът не е вързан за IP.** Мобилните мрежи сменят IP, а кодът за curl е предназначен за ползване от друга машина. IP адресът се записва за одит.

## 6. Лимити

Всички стойности се настройват в **Settings → Upload Protection**.

| Ключ | По подразбиране | Граници | Действие при превишаване |
|---|---|---|---|
| `pass_ttl_hours` | 24 | 1–720 | Нова проверка |
| `pass_max_files` | 20 | 1–10000 | HTTP 429, нова проверка |
| `pass_max_mb` | 5120 | 1–10240 | HTTP 429, нова проверка |
| `max_file_mb` | 2048 | 1–10240 | HTTP 413, проверява се и в браузъра преди качване |
| `passes_per_ip_hour` | 5 | 1–1000 | HTTP 429 при проверка |
| `daily_cap_mb` | 20480 | 1–10485760 | HTTP 429 до полунощ |
| `min_free_gb` | 10 | 0–100000 | HTTP 507, анонимното качване спира |
| `pow_maxnumber` | 50000 | 1000–1000000 | Трудност на proof-of-work |

Твърд лимит, който не се настройва: **30 неуспешни проверки от едно IP за час** блокират ново проверяване за час.

**Опасни файлове** (`block_dangerous`, включено по подразбиране). Блокират се скрити файлове, които започват с точка, като `.htaccess` и `.user.ini`. Блокират се и файлове с разширение `php`, `php3`–`php8`, `phtml`, `pht`, `phps`, `phar`, `cgi`, `pl`, `py`, `shtml`, `htaccess`, `htpasswd`, `asp`, `aspx` или `jsp` в която и да е позиция след първата точка. Пример: `x.php.jpg` се блокира, а `php-notes.txt` минава.

**IP адресът** се взема само от `REMOTE_ADDR`. Прокси хедърите се контролират от клиента и биха позволили заобикаляне на лимитите. Ако WebShare стои зад reverse proxy, настрой `mod_remoteip` в Apache.

## 7. Apache филтър

PHP вижда заявката едва след като целият файл е получен. Без филтър бот без пропуск би прехвърлил 10 GB, преди да бъде отказан. Затова `src/.htaccess` отказва с 403 POST заявки към `/u`, `/u.php`, `/upload`, `/upload.php` и `/u/ИМЕ`, ако **няма нито едно** от:

- параметър `guard=` или `pass=` в URL;
- хедър `X-Upload-Pass`;
- бисквитка `ws_upass`, `PHPSESSID` или `ws_remember`;
- curl или wget в User-Agent, когато е разрешено качване от curl без код.

`.htaccess` не може да чете JSON. Затова PHP поддържа два флаг-файла, които Apache проверява с `-f`:

| Файл | Съществува, когато |
|---|---|
| `src/.upload-guard-on` | режимът е `verified` |
| `src/.upload-guard-curl-open` | режимът е `verified` и `curl_without_pass` е включено |

Флаговете се синхронизират при всяко зареждане на страницата за качване и при запис от админ панела.

**Измерено:** при отказ curl изпраща около 112 KB от файл с размер 3 MB. Останалото не се прехвърля.

**Ограничение.** Филтърът проверява само наличието на бисквитка или хедър, не валидността им. Бот с фалшива бисквитка минава филтъра и се отказва от PHP след прехвърлянето. Срещу това пазят дневният лимит, прагът за диска и `LimitRequestBody` на ниво сървър, ако е нужно.

## 8. Качване от терминал

```bash
# 1. Отвори https://ДОМЕЙН/u в браузър, потвърди и копирай кода
# 2. Качи:
curl -H "X-Upload-Pass: ABCD-EFGH" -F "file=@doc.pdf" https://ДОМЕЙН/u

# Към папката на конкретен потребител:
curl -H "X-Upload-Pass: ABCD-EFGH" -F "file=@doc.pdf" https://ДОМЕЙН/u/ИМЕ
```

Без код curl получава текстов отговор с инструкции:

```
ERROR: Upload verification required.

Open https://ДОМЕЙН/u in a browser, confirm you are not a robot and copy your upload code.
Then upload with:
  curl -H "X-Upload-Pass: CODE" -F "file=@FILE" https://ДОМЕЙН/u
```

**За собствени скриптове** ползвай API ключ и `api-upload.php`. API ключовете не минават през Upload Guard.

**Качване от curl без код** (`curl_without_pass`) връща старото поведение само за клиенти с `curl` или `wget` в User-Agent. Правилото е едно и също в Apache и в PHP, виж D-009. Изключено е по подразбиране, защото User-Agent се фалшифицира тривиално.

## 9. Бутонът „Stop“ и изтриването

**Старо поведение, преди 3.7.0.** POST с `delete_partial=ИМЕ` към страницата за качване изтриваше файл с това име от целевата папка, без каквато и да е проверка. При прекъснато качване PHP не записва файла в целевата папка, така че реално се изтриваше вече съществуващ, често чужд файл. Уязвимостта беше потвърдена на живо.

**Ново поведение.** Изтрива се само файл, който е качен **със същия пропуск** през последните 15 минути. Търсенето първо сравнява крайното име, после оригиналното, и избира най-новия файл. Квотата на пропуска се възстановява. Без пропуск, включително за влезли потребители на `/u`, нищо не се трие. Прекъснатото качване се почиства автоматично от PHP.

## 10. Админ панел

**Settings → Public Access**
- Избор на режим за `/u`.

**Settings → Upload Protection**
- Метод за проверка и ключове за Turnstile.
- Всички лимити от раздел 6.
- Блокиране на опасни файлове, имейл известие и качване от curl без код.
- Статистика за днешния анонимен обем и броя активни пропуски.
- Таблица с активните пропуски: код, време на създаване, срок, IP, брой файлове и обем. При посочване на броя се виждат имената на файловете. Бутонът **Revoke** отменя пропуск веднага.

**Известие по имейл.** Праща се при всяко анонимно качване, ако имейл настройките са активни. Получател е `mail.notify_email` или `mail.smtp_user`. Писмото се праща след отговора към посетителя чрез `fastcgi_finish_request`, така че SMTP не забавя качването.

## 11. Данни

Всички файлове са в `src/`, с права 0600 или 0700 и собственик `www-data`. Apache ги блокира, защото започват с точка. Добавени са в `.gitignore`.

| Път | Съдържание |
|---|---|
| `.upload-passes/{id}.json` | Един пропуск: код, срокове, IP, User-Agent, метод, квоти, качени файлове |
| `.upload-passes/code-{CODE}.json` | Индекс от кода към идентификатора |
| `.upload-guard.key` | HMAC ключ за подписване на задачите. Генерира се автоматично. |
| `.upload-guard-state.json` | Използвани задачи, издадени пропуски и неуспешни опити по IP за последния час, дневни обеми за 7 дни |
| `.upload-guard-on`, `.upload-guard-curl-open` | Флагове за Apache филтъра |

Записите минават през `flock` с изключително заключване, за да не се губят данни при паралелни заявки. Изтекли пропуски се пазят 7 дни за одит и после се трият. Почистването тече при около едно на 50 зареждания на страницата.

**Ротация на ключа.** Изтриването на `.upload-guard.key` обезсилва само издадените, но още нерешени задачи. Издадените пропуски остават валидни.

## 13. HTTP API на страницата

| Заявка | Отговор |
|---|---|
| `GET /u?guard=status` | `{required, pass, reason}` |
| `GET /u?guard=challenge` | Задача за proof-of-work |
| `POST /u?guard=verify` с JSON `{"pow": {...}}` или `{"turnstile": "token"}` | `{success, pass}` и бисквитка |
| `POST /u` с файл | Както досега, плюс `pass` с оставащата квота |

Кодове за грешка в полето `guard` при AJAX качване: `pass_required`, `quota_files`, `quota_bytes`, `file_too_large`, `blocked_type`, `daily_cap`, `disk_low`. При проверка: `ip_pass_limit`, `ip_fail_limit`, `verification_failed`.

## 15. Отстраняване на проблеми

| Симптом | Причина и решение |
|---|---|
| 403 при всяко качване от браузър | Бисквитките са блокирани. Посетителят ползва кода с curl или разрешава бисквитки. |
| Админ настройките не се записват | `.config.json` не е записваем от `www-data`. На dev сървъра това беше така от 2026-02-02. Поправено с `chown www-data:www-data` и `chmod 640`. |
| Проверката казва, че браузърът не се поддържа | Сайтът е отворен по HTTP. Web Crypto работи само по HTTPS. |
| Много потребители от една мрежа удрят лимита | Споделено IP зад NAT. На webshare.techbg.net всички заявки от локалната мрежа идват от 192.168.22.1, затова лимитът от 5 пропуска на час е общ за целия офис. Вдигни `passes_per_ip_hour`. Изключение за доверени мрежи е записано като бъдеща точка F9 в одита. |
| Turnstile не се показва | Липсва ключ. Виж предупреждението в админ панела. |
